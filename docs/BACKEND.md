# Community backend (Supabase)

The forums, sign-in and optional progress backup use [Supabase](https://supabase.com): Postgres, Auth and the auto-generated Data API. The app talks to the database directly with the **publishable key**. All rules are enforced in the database by row-level security, column grants, triggers and a few functions, so the client is never trusted.

Without a backend configured (no `SUPABASE_URL`), the app uses an on-device demo community, and everything else works offline.

## What's in the schema

The schema lives in `supabase/migrations/`. The first file below holds all the tables and logic; the second fills reference data.

**`20261009000000_community.sql`**

*Tables*

| Table | Purpose |
|---|---|
| `profiles` | Created automatically on sign-up with a generated display name like `user_1a2b3c4d`. Users can change their name. Moderation fields (silence, ban) can't be written by users. |
| `user_roles` | Grants `moderator` or `admin`. Users can only read their own roles. |
| `categories`, `parashot` | Reference data. Readable by everyone. |
| `threads`, `posts` | The forum content. |
| `post_revisions` | Edit history. Readable only by moderators. |
| `reactions` | "Todah" reactions. |
| `reports` | Users file reports and can see their own; moderators see all. |
| `user_blocks` | Each user's blocks. Private to that user. |
| `moderation_log` | A record of every moderator action. |
| `user_progress` | Optional backup of reading progress. Each user can only read and write their own row. |

*Private schema*

The `private` schema is not exposed through the Data API. It holds:
- `banned_terms`: the word filter
- `shabbat_windows` and `settings`: optional blocking of posts on Shabbat
- the helper functions

*Triggers*

- They stamp the author on every insert. A client can't post as someone else.
- They enforce:
  - accepted guidelines
  - not silenced or banned
  - rate limits: 30 seconds between posts for new accounts (5 seconds after that), at most 10 posts a day, at most 3 new threads a day, per-thread slow mode, no duplicate posts, and a link limit
- They run the word filter. Hebrew is folded before matching (vowels and cantillation removed, final letters normalized), so adding nikud doesn't get around it.
- They hide a post automatically once three different users report it.

*Functions*

| Function | What it does |
|---|---|
| `accept_terms()` | Records that the user accepted the guidelines. |
| `soft_delete_post()` | Soft-deletes a post. |
| `moderate()` | Moderator actions: hide or restore posts; lock, pin or delete threads; silence, ban or unban users; set trust levels; resolve or dismiss reports. Each action is logged. |
| `delete_my_account()` | Deletes the user's posts, any threads they started that have no posts left, and the auth user. Profiles, roles, blocks, reports, reactions and the progress backup are removed by cascade. |
| `ensure_weekly_thread(p_parasha_id, p_hebrew_year)` | Returns the weekly thread for a parsha, creating it if it doesn't exist. The title is built on the server from `parashot`. |
| `my_profile()`, `create_thread()` | Helpers called by the app. |

**`20261009000100_reference_data.sql`**

The forum categories (including the moderator-only *Announcements*) and all 54 parashot. It is generated by `tool/data/gen_supabase_reference.py`.

`supabase/tests/run_tests.sh` applies the migrations to a temporary PostgreSQL server (with a stub of Supabase's `auth` schema) and checks every policy and trigger. CI runs it on every pull request.

## Setting up a hosted project

1. **Create a project** at supabase.com. Pick a region near your users.

2. **Apply the migrations.** With the [Supabase CLI](https://supabase.com/docs/guides/cli):

   ```sh
   supabase login
   supabase link --project-ref <your-project-ref>
   supabase db push
   ```

   Or paste the two files from `supabase/migrations/` into the SQL editor, in filename order.

3. **Configure email sign-in** under *Authentication → Sign In / Providers → Email*:
   - **Email provider:** enabled.
   - **Confirm email:** off. The code the user types is itself the proof of ownership.
   - **Email OTP length:** 6. **Email OTP expiration:** 900 seconds.

4. **Edit the email templates** under *Authentication → Emails → Templates*. Set both **Magic Link** and **Confirm signup** to the contents of `supabase/templates/magic_link.html`, with the subject *Your Shnayim Mikra sign-in code*.

   The template must contain `{{ .Token }}`, because the app asks for the six-digit code and never opens a link. The default templates only contain a link, and with them nobody can sign in.

5. **Set up custom SMTP** under *Authentication → Emails → SMTP settings*. Supabase's built-in mail service is only for testing: it sends very few emails per hour, and only to your team's addresses. Use a provider such as Amazon SES, Postmark, Resend or Mailgun, and set up SPF, DKIM and DMARC for the sending domain.

6. **Set rate limits** under *Authentication → Rate Limits*. Start with about 30 emails and 30 verifications per hour, and adjust to your traffic.

7. **Build the app with the project's URL and publishable key** (*Project Settings → API Keys*):

   ```sh
   flutter build <platform> \
     --dart-define=SUPABASE_URL=https://<ref>.supabase.co \
     --dart-define=SUPABASE_PUBLISHABLE_KEY=sb_publishable_... \
     --dart-define=SUPPORT_EMAIL=support@example.org
   ```

   For CI, set these as repository **variables** (not secrets) named `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY` and `SUPPORT_EMAIL`. The publishable key is designed to be public.

   **Never put the secret key (`service_role`) in the app or in CI variables.**

8. **Check the security advisors.** Open *Advisors → Security* (or run `supabase db lint`) and confirm there are no warnings about RLS or exposed functions.

## Running moderation

**Appoint a moderator** in the SQL editor. Find the user's id under *Authentication → Users*:

```sql
insert into public.user_roles (user_id, role) values ('<user uuid>', 'moderator');
```

Moderators see *Reports to review* under *Community → Account*.

**Add filtered terms.** Patterns are POSIX regular expressions, matched case-insensitively after Hebrew folding. `reject` blocks the post; `hold` publishes it hidden, for review:

```sql
insert into private.banned_terms (pattern, action, note) values ('\mexample\M', 'reject', 'spam');
```

**Block posting on Shabbat** (optional, off by default):

```sql
update private.settings set value = 'true' where key = 'block_posting_on_shabbat';
-- Fill private.shabbat_windows (region, starts_at, ends_at) for the year, e.g. from hebcal,
-- and set profiles.shabbat_region for users outside the default region ('jerusalem').
```

Keep the community guidelines and the contact address in the app (*About → Community guidelines* and the `SUPPORT_EMAIL` setting) current. Apple and Google both require a published way to report problems, and timely action on reports.

## Local development

```sh
supabase start                 # Postgres, Auth, Studio and an email catcher, in Docker
supabase status                # prints the local API URL and publishable key
flutter run --dart-define=SUPABASE_URL=http://127.0.0.1:54321 \
            --dart-define=SUPABASE_PUBLISHABLE_KEY=<local key>
```

`supabase/config.toml` already sets up six-digit codes and the template. Sign-in emails appear in the local email catcher at http://127.0.0.1:54324.

On an Android emulator, use `http://10.0.2.2:54321` instead of `127.0.0.1`.

## Changing the schema

- Add a new timestamped file to `supabase/migrations/`. Never edit a migration that has already been applied.
- Add a case to `supabase/tests/behavior.sql` for every new policy or trigger, and run `supabase/tests/run_tests.sh`.
- If the change affects the app, update `SupabaseForumRepository`. Also update `DemoForumRepository` so the demo behaves the same way.

## Privacy notes

- The backend holds: email addresses (in Supabase Auth), display names, posts, reactions, reports, blocks, and the optional progress backup.
- Reading progress leaves the device only if the user turns on *Cloud backup*.
- Account deletion is immediate. It covers all of the user's posts and the threads they started that have no other posts.
- Update the privacy policy in the app (`lib/features/about/legal_screen.dart`) if you add analytics, crash reporting or any other processor. The current text says there is no advertising, analytics or tracking.
